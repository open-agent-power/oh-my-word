### 撰写要点

以下混合了法规要求与写作建议；不得把建议、一般规则和审查示例当成无例外禁令。

#### 发明名称

- 应清楚、简要地反映要求保护的主题和类型，与请求书中的名称一致
- 一般不超过 25 字，特殊情况不超过 40 字
- **不得含**：人名、地名、商标、型号、商品名称；「专利」「新型」「改进」等非技术用语
- **不得使用**标点（必要的括号除外）
- 名称与实际主题匹配；“一种”不是法定必填前缀，外观设计应直接写产品名称。

#### 权利要求书

- 编号用阿拉伯数字顺序编号：`1.` `2.` `3.`
- **第一项必须是独立权利要求**，且写在所有从属权利要求之前
- 独立权利要求应包含**前序部分**（主题名称 + 与最接近现有技术共有的必要技术特征）
  和**特征部分**（`其特征在于` + 区别技术特征）；发明性质不适合两段式的，可以其他方式撰写。
- 从属权利要求开头写「根据权利要求X所述的……」，**只能引用在前的权利要求**
- 多项从属权利要求只能以择一方式引用
- **不得使用**「最好是」「例如」「尤其是」「必要时」「大约」「左右」等含义不确定的用语
- 除绝对必要外，不得使用「如说明书……部分所述」「如图……所示」
- **不得有插图**（化学式、数学式可以）
- **每一项权利要求只允许在结尾处使用一个句号**。分项列举的步骤/部件，段末用**分号**，
  最后一项才用句号（官方 `100001权利要求书` 背面「注意事项」第五条）
- 科技术语须与说明书逐字一致（官方「注意事项」第四条）
- 每页下框线居中顺序编写页码（同「注意事项」第六条）

关于独立权利要求的数量：法条说「一项发明应当只有一个独立权利要求」，但
**符合单一性时可以写两项以上**（第一独权 + 并列独权）。《审查指南》第二部分
第六章 2.2.1 列出六种允许组合，最常用的是「方法 + 为实施该方法而专门设计的
设备」。写双独权是合法的，自检只会给 `WARNING` 提示复核单一性。

#### 说明书

通常按以下结构组织；无附图时不编造附图说明，性质特殊时按实施细则允许方式清楚撰写：

```
【技术领域】 → 【背景技术】 → 【发明内容】 → 【附图说明】 → 【具体实施方式】
```

- **技术领域**：一句话写清本发明所属或直接应用的技术领域
- **背景技术**：写明对发明的理解、检索、审查有用的背景技术，并**指出现有技术
  存在的缺陷**。不要贬低他人产品，客观陈述
- **发明内容**：写清三件事——要解决的技术问题、技术方案、有益效果。
  技术方案应与独立权利要求一致，但可以写得更完整
- **附图说明**：逐幅写明「图1为……示意图」。附图要有标号
- **具体实施方式**：**这是说明书最重要的部分**。必须详细到「本领域技术人员
  能够实现」的程度。只给一个实施例时，权利要求的保护范围就很容易被限缩。
  建议给出多个实施例以支撑上位概括

引用的图号必须真实存在。正文提到「图2」就必须有图2。

#### 领域披露

从 [领域目录](../references/domain-catalog.md) 读取与技术贡献匹配的子 Skill，按其适用条件补齐信息槽。软件/AI 的构建训练与应用披露见 [软件模块](../domains/patent-software-ai/SKILL.md)；其他领域同样按需加载。领域问题不得转化为所有稿件必填项，关键词检查通过也不等于公开充分。

#### 摘要

- 写明技术问题、技术方案要点、主要用途
- **不超过 300 字**（含标点）
- **不得使用商业性宣传用语**：「最佳」「首创」「领先」「填补空白」等一律不能用
- 有附图时必须指定一幅摘要附图（不指定则取编号最小的那幅）

#### 实用新型的额外限制

这两条是最常见的实质缺陷，务必检查：

1. **必须有附图**。说明书应当有表示产品形状、构造或其结合的附图，不能省略
2. **只能有产品权利要求**。方法、工艺、用途类的主题实用新型保护不了，
   应改为申请发明专利

#### 外观设计的简要说明

应当写明（脚本会按法定顺序编号输出）：

1. 产品名称
2. 产品用途
3. **设计要点**（通常在于产品的形状）
4. 最能表明设计要点的图片或照片
5. 必要时：省略视图的情况、是否请求保护色彩

### 稿件格式

带 YAML frontmatter 的 Markdown：

```markdown
---
title: 一种基于边缘计算的智能水表数据采集方法
type: invention
applicant: 示例科技有限公司
inventors: [张三, 李四]
---

# 权利要求书

1. 一种……，其特征在于，……
2. 根据权利要求1所述的……，其特征在于，……

# 说明书

## 技术领域
……

## 背景技术
……

## 发明内容

### 要解决的技术问题
……

### 技术方案
……

### 有益效果
……

## 附图说明
图1为……示意图。

## 具体实施方式
参照图1，……

# 摘要
……
```

附图用 Markdown 图片语法，路径可以是本地文件：

```markdown
# 附图

![图1](图1.png)
![图2 摘要附图](图2.png)
```

或在 frontmatter 里结构化声明（外观设计常用）：

```yaml
drawings:
  - {number: 1, caption: 主视图, path: 主视图.png}
  - {number: 7, caption: 立体图, path: 立体图.png, abstract: true}
```

路径的相对基准是**稿件文件所在目录**，不是运行目录——稿件和它的
`figures/`、`images/` 是一个整体，能整体搬移，也能从任意工作目录构建。

### 生成之后必须核对图真的进去了

`lint` 通过 ≠ 图在文件里。附图说明写了图1、图2，而图件没产出或路径写错时，
`build` 不会失败：它会在图位写一行「（图N缺失）」占位句，成品看起来完整，
打开才发现说明书有图号没有图。这是本项目真实发生过的一次交付事故。

所以生成完申请文件后，把 `.docx` 当 zip 拆开点数：

```python
import zipfile
z = zipfile.ZipFile("申请文件.docx")
doc = z.read("word/document.xml").decode("utf-8")
print(len([n for n in z.namelist() if n.startswith("word/media/")]), "张图")
print(doc.count("<w:drawing>"), "处插图")
assert "缺失" not in doc
```

图中的插图数应当等于「附图说明的幅数 + 摘要附图 1 幅」（摘要附图与某幅
说明书附图共用同一个图件文件，所以 media 数会比 drawing 数少 1）。

自检侧的两条守卫：`DRAW-001` 附图说明有措辞却没登记图件（警告）、
`DRAW-002` 登记了路径但文件不在（错误）。交付前这两条都应当为零。

解析层很宽容：`【技术领域】`、`一、技术领域`、`技术领域：` 都认；权利要求
不带编号时按空行分段；无法归类的章节会保留而不是丢弃。

### 命令行参考

```bash
python tools/patent.py info     稿件.md            # 确认稿件被正确理解
python tools/patent.py lint     稿件.md            # 形式合规自检
python tools/patent.py build    稿件.md -o 出.docx  # 生成申请文件
python tools/patent.py template design -o 稿件.md   # 生成骨架
```

版面选项（`build` 可用）：

| 选项 | 说明 |
| --- | --- |
| `--font 宋体\|仿宋\|楷体` | 正文汉字字体，默认宋体 |
| `--font-size 12` | 正文字号（磅），工具范围10~14pt，不能由名义字号直接认定实际字高合格 |
| `--line-spacing 1.25` | 行距倍数，**默认 1.25**。实测 12pt 宋体行间空白 2.96mm，落在 2.5~3.5mm 内；1.5 倍为 4.32mm，**超上限**，不要用 |
| `--subsection-style inline\|keep\|flatten` | 「发明内容」三级小标题的处理方式。**默认 `inline`**，把「技术方案：」这类小标题并入段落做加粗引导词，最接近代理师的正式稿 |
| `--bold-sections` | 章节标题加粗（默认不加粗） |
| `--split` | 每部分独立成文件 |
| `--no-page-numbers` | **默认已输出页码**（各部分分别编号、页脚居中、下沿距底 15mm）；只在做纯屏幕审阅稿时用它关掉 |
| `--strict` | 自检有错误则拒绝生成 |
| `--type` | 覆盖稿件的专利类型 |

`lint` 加 `--json` 可输出结构化结果，便于在流程里判断。

## 第 3 步 · 先自检，再生成

```bash
# 先看自检结果，根据 ERROR 逐条修正
python tools/patent.py lint 稿件.md

# 完成08内容审查后生成；--final 拒绝不完整、过期或未闭合证据
python tools/patent.py build 稿件.md -o outputs/审阅稿.docx --final --facts outputs/TECH_FACTS.json --review outputs/content-review.json
```

**务必先 `lint` 再 `build`。** 直接 build 会把错误带进最终文件。
自检的读法与修正流程见 `07-self-check.md`。

需要官方转换交接时：

```bash
python tools/patent.py handoff 稿件.md -o outputs/cnipa-handoff --facts outputs/TECH_FACTS.json --review outputs/content-review.json
```

页码默认输出（各部分分别编号、页脚居中、下沿距底 15mm），不需要再传 `--page-numbers`；
只有做纯屏幕审阅稿时才用 `--no-page-numbers` 关掉。

交接包拆分各文书并分离摘要附图；DOCX 仍须通过官方工具或编辑功能制作符合数据标准的 XML 后核对。

## 交付前自查

- [ ] 稿件里没有残留的「待补充」「XXX」一类占位符（`TXT-001` 会拦）
- [ ] 修正过的地方**重新跑过一遍 `lint`**，不是假设改对了
- [ ] 自检里发现的「是否合格」类问题，已经改到稿件里，而不是只写在报告里
- [ ] **自检清单本身没有写进申请文件正文**。正文里出现「自检」二字即不合格

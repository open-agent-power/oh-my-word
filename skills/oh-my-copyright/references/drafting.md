# 软著材料的文本起草与审阅

本页选择性适配已固定的 Fokkyp 2.6 业务理解与手册方法，许可及原件见 [复用记录](../../../docs/05-fokkyp-reuse.md)。不安装本项目后端也可按此整理、起草或审阅文本；选用工具制作时再进入原流程。

## 输入与缺口

写前读 [本域来源](domain-sources.md)。确认软件名称/版本、用途、目标使用者、真实功能、运行入口、操作限制和可核对的结果。软件技术口径与正式登记口径分开；权利人、完成日期、权属基础及真实环境不能从仓库组织、Git 时间或本机配置推断。

只写手册或审阅时，不强迫补齐所有申请字段。缺少操作依据，先完成有材料支持的章节，把所需界面、命令或说明列为问题；不把技术草稿称为完整正式登记包。已有确认与授权直接复用。

## 组织与写作

1. 用项目证据写清“谁在什么场景用它完成什么任务”。将功能对应材料位置，区分当前功能、计划功能和行业参考；分析工具或目录结构只帮助找材料。
2. 按真实用户任务和流程组织手册。主要任务说明进入位置、操作、输入/状态约束及可观察反馈，写成自然段或确有顺序的步骤。不只列抽象功能，不为每个模块套相同小标题。
3. GUI 写实际控件和反馈；CLI/库写真实调用、前提及返回/回显，不改写成按钮页面。声明“实际运行”前核对命令和输出；只有文档示例时说明来源及未运行状态。
4. 系统要求、FAQ、术语、相关文档只写真实且有用的内容。没有配置测试不编最低 CPU/内存；没有设计文档不列虚构文件。截图缺失列在辅助问题中，不伪造窗口。
5. 申请填写辅助、手册和源码范围保持名称、版本、功能口径一致，字段按 [字段规则](application-fields.md) 核对。需要源码材料时才确定完整程序范围与选择，不把候选清单当作整个程序。

自然表达来自具体对象、动作、条件和反馈，不靠替换“AI 常用词”。适当列表、步骤和表格可以帮助阅读，不强制固定数量的功能、FAQ、自检轮次。

## 注释示例

以下为本项目编写的示意，不是某软件真实操作记录。

**材料只有命令行入口，初稿写“管理员登录控制台并点击开始”。** 这增加了没有依据的角色和界面。回到实际命令和参数，说明调用、输入前提及输出；无运行记录不编成功回显。

**初稿写“支持智能分析，显著提高效率”。** 它没有说明用户任务，也缺少效率依据。若本案证实读取本地 CSV 并生成汇总表，改写为具体输入、调用和输出；CSV、路径和反馈仍须取自本案，不复制本例。效率结论需要相应测量。

## 审阅与交付

逐项定位问题、依据、修订或待补材料：

- 用途、功能、操作是否有依据，当前/拟议状态是否分开？
- 关键任务的前提、限制、错误和反馈是否准确，能否据此理解操作？
- 名称、版本、字段、范围是否一致，是否把部分摘录写成完整程序？
- 是否编造权属、日期、配置、截图或效果，是否借同行材料增加功能？
- 是否有重复模块、套话或无助使用的内部细节，是否因改文风丢失条件？

文本路径交付正文或审阅意见，来源及未确认项留在辅助说明；不产生 CLI 的 reviewed/final 状态。Word/PDF、源码摘录或完整包使用现有工具，补齐其事实与审阅要求。文本自查不代替当期办理核验、权属确认或登记受理。

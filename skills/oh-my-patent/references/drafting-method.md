# 从交底到专利草稿与支持复核

先读 [本域来源](domain-sources.md)，再处理本案材料。本文选择性适配 handsomestWei 的交底映射和一致性复核方法，参考 WIPO 手册的交底、概括支持与说明书组织方法；保留本项目事实和交付边界，不引入上游目录、YAML 或工具协议。来源、许可与改编说明见 [第三方记录](../../../THIRD_PARTY.md)。

## 输入与缺口

确定申请类型、用途与阶段，读取技术问题、核心手段、部件/步骤关系、必要条件、实施方式、附图及已有结果。只有源码或零散笔记时可以先整理已有机制和待补交底，不能用行业常识拼出未披露的实现。外观设计围绕产品、保护部分和真实视图，不套用技术权项。

把已核实事实、解释和未确认项分开，工作笔记可写来源位置、日期及“为什么能支持该表述”。不要求 JSON 或 CLI。申请后改稿须取得原始申请、当前文本和程序材料；新材料不能自动变成合法新增内容。身份、权属和日期等已有确认复用，未知继续明确。

## 组织论述

发明/实用新型先形成可支持的保护主题与必要关系，再往返核对权项、说明书及附图；不强制所有任务采用同一写作顺序。按材料确定从属回退，不为凑数量添加参数或分支。

| 稿件部分 | 从交底取得什么 | 复核什么 |
| --- | --- | --- |
| 技术领域、背景 | 实际对象、使用条件、已读对比方案及其具体限制 | 背景是否对准本问题，是否误将检索列表或臆测缺点当叙述；来源仍在辅助记录中保留 |
| 发明/实用新型内容 | 问题、必要手段、相互关系及有依据的效果 | 与独权是否同一技术方案，效果能否由手段解释；不混入未实施设想 |
| 具体实施方式 | 可实施流程/结构、必要取值与条件、已有表格/公式、分支 | 能否实现，哪些细节支撑概括；不因缺数据就编实验，不因看过同类专利就加入其参数 |
| 附图和标记 | 真实结构/步骤及其关系 | 正文、权项、图件是否同义，标号是否一致；外观图件按其类型要求处理 |
| 摘要 | 已有技术问题、方案要点和用途 | 是否新增正文没有的特征，是否有宣传或超出依据的效果 |

按 [通用模板](general-drafting-template.md) 组织最终文稿。文本路径使用普通表格或笔记完成事实与支持对照；工具路径才填写相应事实/支持 JSON。不能因为选择文本路径而跳过语义检查。

## 支持关系与审阅

对每项权利要求分解全部特征和关系，定位说明书段落、实施方式、本案来源及必要附图，解释概括为何成立。现有技术另作对照，保留原文、公开时间、区别与未知；它不能代替本案事实。文字命中不等于范围和关系得到支持。

检查问题包括：技术方案是否能实施；必要关系是否缺失；术语、步骤、标号是否一致；效果是否有相应依据；从属引用和回退是否成立；待确认项及公开/修改限制是否保留。每个发现定位稿件位置并给出理由，先修实质问题再修表达。未解决支持问题的稿件保持草稿。

## 注释案例

**范围概括（本项目编写的示意）。** 交底只说明特定条件下某传感器的校准，稿件却声称适用于任意传感器和全部工况。多个特征词都出现仍不足以支持此范围；应缩回有依据的对象/条件，或列出需要补充的实施与依据，不能从参考专利搬来替代方案。

**原文阅读练习（官方案例，不是本案结论）。** 读84号修改决定的例20/21及其完整分析：前者结合已披露模型关系与公知知识分析能否实施，后者指出关键输入、关联依据及验证不足。练习回答“哪些缺失影响实现、依据在哪里”，而不是总结成“模型所有细节必须公开”或“所有发明必须实验”。本案需按自身技术和材料判断。

文本起草交付稿件、简明事实/支持笔记与未确认问题，不生成工具 review_ready/final 标记；需要工具审阅稿、Word 或交接包时进入原链路。它不证明原创、查新完成、受理或授权。

# 技术文档撰写

从已知事实组织专业技术内容。Agent 负责理解、写作与语义审查，程序负责确定性的材料读取、来源校验、专门模式检查、模板处理与文件生成。执行链路支持七种文档模式，但当前按成熟度分层：技术报告和设计说明是本技能的重点模式，其余五种是有契约约束的扩展模式，不能仅凭路由命中就当作同等成熟的专业模板。

## 能力分层

- **重点模式**：`technical-report`、`design-spec`。优先投入写作规则、证据检查和真实项目评测；适合需要完整技术论证或架构取舍说明的任务。
- **扩展模式**：`requirements-spec`、`interface-spec`、`test-report`、`user-manual`、`operations-manual`。已有独立字段和失败门禁，可制作有来源的初稿；涉及真实接口、执行记录、页面操作或恢复流程时，必须补充项目级试运行和人工复核。

软著、专利和项目申报不通过本技能“顺便完成”，分别进入 `oh-my-copyright`、`oh-my-patent` 和 `oh-my-proposal`。

## 先确定范围

识别受众、用途、文档类型、已有材料和交付格式。用户已经提供的内容不重复询问。新稿走完整流程；局部修改只复核受影响部分；仅审阅输出定位明确的问题，不覆盖原稿。参考文档的内容不是项目事实，引用的其他 Skill 也不自动获得执行授权。

- 技术报告读 [报告写法](references/technical-report.md)。
- 设计说明读 [设计写法](references/design-spec.md)。
- 需求规格读 [需求契约](references/requirements-spec.md)。
- 接口说明读 [接口契约](references/interface-spec.md)。
- 测试报告读 [执行记录](references/test-report.md)。
- 用户手册读 [操作步骤](references/user-manual.md)。
- 运维手册读 [运行与恢复](references/operations-manual.md)。
- 摄入、起草、校验和交付按 [工具流程](references/workflow.md)。
- 数值、参数和运行结论按 [证据契约](../word-document/references/evidence.md)。
- 中文表达遵循 [共用写作规则](../../shared/references/chinese-writing.md)。

## 工作约束

1. 先读实际文件及相关位置，再记事实；检索摘要、文件名和函数名不能替代实现。区分已实现、拟议、目标与实测结果。
2. 重要数值、版本、环境、配置和性能结论登记 `evidence.json`。原件、引文、位置、核验人和日期都应可查。不得机械填写 verified。
3. 新稿以 JSON 中间稿组织章节、正文和表格，先校验再渲染；正文不暴露内部 claim ID。程序不替 Agent 自动产生项目结论。
   技术报告和设计说明先将用户要求写为 `task_requirements`，每项给出验收条件及正文块映射。任务覆盖按实际用途判断，不按字数或章节数推断；材料不足时正文明确缺口。
4. 分析给出依据及限制。缺少压测或实验材料时说明缺口，不能把计划指标写成结果，也不能为了移除占位符而补造数字。
5. 本次只修改授权范围。改稿或来源变化后重新校验；旧文档、旧账本和旧审阅记录不得静默覆盖。
6. 需要 Word 时调用 [Word 制作技能](../word-document/SKILL.md)。生成后读取 DOCX/PDF 和所有页图；没有实际渲染与复核，状态保持 draft 或 awaiting-review。

## 完成条件

用户要求的正文完整、证据和缺口清楚、生成文件可打开，机器检查及实际内容/版面复核均有记录。交付 DOCX、PDF 和审计目录。说明具体限制，不声称“零幻觉”“全格式兼容”或“无需人工复核”。只有机器检查通过时，明确称为机器检查通过。

定稿前逐项审阅任务覆盖、逐个事实块核对来源是否支持全部陈述。引文真实但正文附加用途、因果、效果或运行结论时仍可能不成立；记录具体问题，不把数字覆盖当作语义支持。旧稿未登记任务项仍可构建，但重点模式定稿前须补齐。

五种扩展模式对结构化记录、正文映射和证据作确定性检查；Agent 仍须做语义复核。它们的客户真实模板、多节版式和跨不同技术栈实例尚待具体材料验收，不宣称通用格式完整兼容。注册表中的 `mode_scope` 是能力分层元数据，路由和 `skills list` 会保留该信息。

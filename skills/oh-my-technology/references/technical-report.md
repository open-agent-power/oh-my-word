# 技术报告

读者需要知道技术解决了什么问题、怎样实现和验证、哪些结论可用以及适用边界。先确定是实施总结、研发报告还是验证性报告；缺少运行证据时可以交付源码分析报告，但标题、结论和正文必须反映实际范围。

对应契约：`word_skills/schemas/technical-report.yaml`，按 ID 识别章节，允许标题按受众改写。

| ID | 应回答的问题 |
|---|---|
| background | 对象、现状、受众和本次范围是什么 |
| objectives | 项目要解决什么；目标与已有结果分别是什么 |
| methods | 采用什么资料、方法和验证条件；能证明什么 |
| implementation | 关键机制、模块、技术取舍及实现依据是什么 |
| results | 实际观察到了什么；没有验证什么；是否满足有依据的验收要求 |
| risks | 风险、局限、后续建议和可使用的结论是什么 |

技术报告不强制使用实验论文格式。代码审阅、架构分析和实际测试应明确区分。表格适合参数、模块、对比与验证记录；长段推理用正文。图示只有在解释机制时才加入，原始数据不足不得生成“实验曲线”。

审阅时检查：结论是否超出方法和样本范围；单位、版本和基线是否一致；建议是否冒充已部署功能；源码可见的能力是否被夸大为实际性能或业务效果。

将本次用户要求拆为可验收的 `task_requirements`，而不是把六个默认章节当作完成标准。例如涉及容器化部署时，根据用途覆盖环境依赖、服务拓扑、关键配置、启动停止、可观察结果及故障恢复边界；来源只有教程时明确为示例分析，不宣称真实部署成功。有材料而遗漏与确实缺少材料分别记录。

# 技术报告

读者需要知道技术解决了什么问题、怎样实现和验证、哪些结论可用以及适用边界。先确定是实施总结、研发报告还是验证性报告；缺少运行证据时可以交付源码分析报告，但标题、结论和正文必须反映实际范围。

使用可选工具路径时，对应契约为 `word_skills/schemas/technical-report.yaml`，按 ID 识别章节，允许标题按受众改写。直接写文本时，下表用于核对问题覆盖，不要求创建 JSON 或机械凑齐同名章节。

| ID | 应回答的问题 |
|---|---|
| background | 对象、现状、受众和本次范围是什么 |
| objectives | 项目要解决什么；目标与已有结果分别是什么 |
| methods | 采用什么资料、方法和验证条件；能证明什么 |
| implementation | 关键机制、模块、技术取舍及实现依据是什么 |
| results | 实际观察到了什么；没有验证什么；是否满足有依据的验收要求 |
| risks | 风险、局限、后续建议和可使用的结论是什么 |

技术报告不强制使用实验论文格式。代码审阅、架构分析和实际测试应明确区分。表格适合参数、模块、对比与验证记录；长段推理用正文。图示只有在解释机制时才加入，原始数据不足不得生成“实验曲线”。

审阅时检查：结论是否超出方法和样本范围；单位、版本和基线是否一致；建议是否冒充已部署功能；源码可见的能力是否被夸大为实际性能或业务效果。

将本次用户要求拆成可核对的条目，工具路径记录为 `task_requirements`；六个默认章节不是完成标准。例如涉及容器化部署时，根据用途覆盖环境依赖、服务拓扑、关键配置、启动停止、可观察结果及故障恢复边界；来源只有教程时明确为示例分析，不宣称真实部署成功。有材料而遗漏与确实缺少材料分别记录。

## 从材料到正文

先按 [来源页](domain-sources.md) 阅读本次需要的原文。以下方法选择性适配既有 riekelt 来源，并参考 NASA 的报告组织方法；不引入它们的工具、行政要求或个人标点规则。

1. 用读者要完成的任务确定范围。例如架构决策读者需要取舍、代价和风险，复现读者需要条件、步骤和可观察结果；不因材料多就把所有模块逐个介绍。
2. 先整理本次能支持的主要结论与材料位置，再组织论证顺序。将观察、解释、提案分开；无运行记录的源码分析不能推导已测性能。资料不足时先明确能回答什么、不能回答什么。
3. 每个主要章节围绕一个问题展开：主张或发现、依据、解释、适用条件。比较方案时使用相同条件；数据放表中，正文说明关系与边界，不把表里所有数字再重复一遍。
4. 最后复核开头、正文和结论的一致性。先修事实、遗漏与推理，再改表达；每次修订说明具体缺陷，保留本来准确、自然的文字，不为统一句式全篇重写。

## 注释示例

以下为本项目编写的示意例，不是实测结果，不能拿来填本案数字。

**材料只有重试实现，没有并发或故障测试。**

- 不成立：“系统通过三次重试显著提高可用性，并可支撑高并发。”代码没有提供可用率或并发结果，重试次数也不能单独证明业务效果。
- 可写：“实现包含最多三次请求尝试；本次依据源码分析其失败重试路径，尚未提供并发条件下的成功率或延迟记录。”实际次数仍须核对本案源码，不能从本例照搬。

**任务是比较部署方案，初稿却逐文件介绍源码。** 保留能解释方案差异的实现依据，将正文改为相同环境下的部署依赖、运行复杂度和已知风险比较；没有运行材料的项目列为未验证。这样修的是任务覆盖，不能靠补长模块介绍解决。

## 交付前审阅

逐项给出正文位置和依据，存在问题时定位到句子，不只给总体分数：

- 读者要求能否在正文找到回答，缺口是否可见？
- 观察、解释、拟议与实测状态是否清楚，引用能否支持整项结论？
- 条件、基线、单位、版本、样本及失败结果是否保留？
- 主要发现是否能从方法与材料推得，结论有没有扩大适用范围？
- 文字是否解释具体机制和结果，是否有空泛效果、重复套话或无助任务的章节？

这提供写作与检查方法，不是专业盲评，也不保证模型每次遵从。来源身份与许可见 [第三方记录](../../../THIRD_PARTY.md)。
